# What the logging hook records

Approve this before rollout.

## Recorded

Per tool call, one JSON line:

- UTC timestamp
- Repository basename (e.g. `core-api`)
- Session ID and prompt ID (opaque UUIDs generated by Claude Code)
- Tool name (`Read`, `Grep`, `Edit`, `Bash`, …)
- Subagent name, if the call happened inside one
- **Byte counts** of the tool's input and result
- **File basename only** (e.g. `login.py`), when the tool acted on a file

## Not recorded

- No file contents
- No source code
- No prompts or anything the engineer typed
- No Claude responses
- No full paths, so directory structure is not leaked
- No shell command text
- No environment variables, credentials, or tokens

A representative line, in full:

```json
{"ts":"2026-08-10T21:36:39Z","repo":"cc-kit","session":"abc123",
 "prompt_id":"p-1","tool":"Read","agent_type":"main",
 "response_bytes":28,"input_bytes":39,"file":"login.py"}
```

## Where it goes

`~/.claude/usage-logs/YYYY-MM-DD.jsonl` on the engineer's own machine.
Nothing is transmitted anywhere. There is no server, no endpoint, no upload.

If you want a team-wide report, engineers share their log files deliberately,
or run `report.py --json` locally and share only the aggregate. Decide which
before rollout and say so plainly when you announce the kit.

## Opting out

Delete the `PostToolUse` block from `.claude/settings.json`, or set
`"disableAllHooks": true` in `~/.claude/settings.local.json`. Nothing else in
the kit depends on the logs; agents and commands keep working.

## Why basenames and byte counts at all

Byte counts are the metric. Basenames are what let you find the specific
pattern worth fixing — for example, discovering that one 400 KB generated
schema file is read in full at the start of most sessions. Without it you know
context is large but not why, and cannot act on it.

If even basenames are unacceptable, delete the `file:` line from the jq filter
in `.claude/hooks/log-usage.sh`. Everything else still works.
